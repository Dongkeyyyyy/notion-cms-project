## 4단계. 추가 기능 개발

> MVP가 안정화된 뒤, 효과가 큰 순서대로 하나씩 진행한다. 각 기능은 독립된 작업 단위로 완료·검증 후 다음으로 넘어간다.

### 작업 (PRD 13장 향후 확장 기준)

| 순서 | 기능 | 설명 | 예상 시간 |
|---|---|---|---|
| 4-1 | 기간·코인·감정 필터 | URL 쿼리 파라미터(`searchParams`) 기반 필터, 통계도 필터 결과로 재계산 | 1~2시간 |
| 4-2 | 누적 손익 곡선·월별 손익 차트 | 차트 라이브러리 도입(shadcn `chart`/Recharts 등), 집계 함수는 `trade-stats.ts`에 순수 함수로 추가 | 1~2시간 |
| 4-3 | 웹에서 매매 기록 작성 | react-hook-form + zod 폼 → Server Action → Notion 쓰기, sonner 토스트, 저장 후 `revalidatePath` | 2~3시간 |
| 4-4 | 매매 전 원칙 체크리스트 | 진입 전 확인 항목 UI (저장 방식은 Notion 별도 DB 또는 로컬 상태 중 선택) | 1시간 |
| 4-5 | 코인 시세·워치리스트 | CoinGecko 연동, 별도 캐시 전략 | 2시간 이상 |

### 이 순서인 이유
- **필터를 먼저**: 읽기 전용 기능이라 위험이 낮고, 이후 차트가 필터 결과를 그대로 재사용할 수 있다.
- **차트는 그다음**: 기존 데이터만으로 구현되며 감정 패턴 시각화라는 제품 목표에 직접 기여한다.
- **쓰기는 중반 이후**: Notion 쓰기·인증·검증이 필요해 위험도가 높다. 읽기 기능이 안정된 뒤에 도입해야 문제 원인을 분리할 수 있다. 쓰기 도입 시 서버 전용 토큰 보호와 접근 제어(비목표였던 인증)를 함께 검토한다.
- **외부 API(시세)는 마지막**: 외부 의존성이 늘어 장애 지점이 커지므로 가장 나중에 둔다.

### 예상 소요 시간
**약 4~8시간** (선택한 기능 수에 따라 조정)

### 완료 기준
- [ ] 각 기능별로 `lint`·`tsc`·`build` 통과 및 Playwright MCP 시각 확인
- [ ] 필터: URL 공유 시 같은 결과가 재현되고, 결과 0건일 때 `EmptyState`가 표시된다
- [ ] 차트: 합계가 요약 카드 총 손익과 일치한다
- [ ] 쓰기: 폼 제출 후 Notion DB에 행이 생성되고 목록에 반영된다, 검증 실패·API 실패 시 사용자에게 안내된다
- [ ] 추가 기능으로 MVP의 기존 동작(통계 값, 상태 화면)이 깨지지 않는다

### 이 순서인 이유
최적화는 "무엇이 느리고 무엇이 문제인지" 측정할 수 있을 만큼 기능이 갖춰진 뒤에 해야 한다. 먼저 하면 바뀔 코드를 최적화하느라 시간을 낭비한다. 배포를 마지막에 두는 이유는 위의 모든 검증을 통과한 상태로 출시해야 하고, 배포 환경에서만 드러나는 문제(환경변수 누락, 캐시 동작, 도메인 설정)는 실제 배포 후 확인해야 하기 때문이다.

### 예상 소요 시간
**약 1~2시간**

### 완료 기준

- [ ] 클라이언트 번들·소스에서 토큰이 노출되지 않는다
- [ ] 배포 환경에서 환경변수 누락 시 `ErrorState`가 표시된다 (크래시 없음)
- [ ] `npm run lint`, `npx tsc --noEmit`, `npm run build` 통과
- [ ] README에 따라 처음부터 설정 가능함을 확인

## 진행 규칙

1. 각 단계의 **완료 기준을 모두 충족한 뒤** 다음 단계로 넘어간다.
2. 단계가 끝날 때마다 `/check`(필요 시 `/check build`)로 검증하고 커밋한다.
3. 컴포넌트 계층 `ui ← common ← layout ← app`의 단방향 import를 지킨다.
4. 사이트 이름·메뉴는 `config/site.ts`에서만 수정한다.
